# 本地后台任务并发

content-service 每个进程默认有 **4 个后台执行槽位**。未设置环境变量时，独立任务可同时占用这 4 个槽位。`CONTENT_JOB_MAX_WORKERS` 可以显式覆盖默认值，启动时读取；现有服务进程需要重启后才会采用新的默认值。企业身份、SQLite 配置和本地启动方案保持原样。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `CONTENT_JOB_MAX_WORKERS` | `4` | 每进程后台执行槽位 |
| `CONTENT_JOB_MAX_QUEUE` | `1000` | 进程内等待提交的工作数量上限，不含运行槽位 |
| `CONTENT_JOB_TIMEOUT_SECONDS` | 未设置 | 调度器中尚未开始的 Future 到期取消；不能强制终止已运行的 Python 线程 |

正在执行的任务仍依赖现有 Provider 超时、Job lease 和取消检查。同一批次内需要按分镜顺序执行的任务仍按序运行。同步 HTTP 接口不经过这个池；后台槽位不是系统可登录人数或 Provider 配额。

验证采用 Barrier/Event 同步，断言 4 个工作同时运行、第 5 个等待、排队取消后释放名额以及队列饱和拒绝。SQLite 测试使用不同任务、独立 Session 和临时数据库，确认领取及最终结果不串任务。外部模型调用和视频编码的实际吞吐量仍受上游配额和本机 CPU/内存影响，不能用线程数推定。

读取基准提交 100 次列表请求，由 16 个并发客户端 worker 分批发起并逐请求计时；它只衡量列表读取，不代表同时执行 100 个生成任务。
